# Lethe (zec-unlinkable-swaps): judge and production review, 2026-10-21

Reviewed at `e889b4b` as a strict hackathon judge and as a production reviewer. The question was:
does every swap really get a refund address that nothing else ties to the wallet's other swaps, and
does anything in the code or its tooling put those links back?

## Linkability and security findings (file:line on `e889b4b`)

### 1. The dashboard dev server hands out the wallet: seed, NEAR key, demo wallets, index book (HIGH)

`packages/dashboard/vite.config.ts:8` sets `server.fs.allow` to the repository root. Vite's default
deny list covers `.env*`, `*.pem`, `*.crt` and `.git`, so everything else under the repo is served at
`/@fs/<abs path>`. That includes `.demo/` (gitignored, but on disk for anyone who ran the demo). I ran
`pnpm --filter @zswap/dashboard dev` and requested only status codes and sizes, never the contents:

```
.demo/seed                               -> 200   (the wallet seed every refund key derives from)
.demo/near-recipient.json                -> 200   (holds a NEAR private key)
.demo/wallets/provider/zingo-wallet.dat  -> 200   (zingo wallet file)
.demo/index-book.json                    -> 200   (the ledger that links every swap)
README.md                                -> 200
```

Any process on the machine can read these while the dashboard runs, and so can anyone on the LAN
once someone adds `--host`. For a privacy wallet this is the worst kind of leak: one seed links
every refund address.

### 2. Concurrent reservations give two swaps the same index, so the same refundTo (HIGH, the core claim)

`IndexBook.reserve` (`packages/cli/src/lib.ts:74-83`) reads the book, derives a key with a child
process, then writes it back, with no lock. The temporary file name is shared too
(`${path}.tmp`, line 71). The CLI and the MCP server use the same book (`ZSWAP_BOOK`), so the CLI
plus an agent, or two agents, can reserve at the same time. Measured with six processes reserving
at once against a fresh book:

- as shipped: 2–3 of the 6 crash with `ENOENT rename book.json.tmp` (3 runs out of 3);
- with only the temp name made unique: **all six processes got index 0**, which means six public
  quotes with the same `refundTo`. This defeats the product's one guarantee.

`attach` (`:84`) does the same unlocked read-modify-write and can drop a concurrent reservation.

### 3. The destination recipient silently re-links the swaps (MEDIUM-HIGH)

Every quote sends `recipient` in clear to a request that 1Click marks public
(`packages/cli/src/lib.ts:115`). The live run used one NEAR account for all three swaps
(`packages/examples/src/run.ts:48`, and `deployments/testnet.json` `quotes[*].quoteRequest.recipient`).
So the published run *is* linkable: three different `refundTo`, one `recipient`. The docs mention
this as a limit, but the CLI and the MCP `safe_quote` tool let an agent reuse a recipient without any
warning. That is the most likely way an agent undoes the whole design.

### 4. A wallet restored from its seed cannot find its refunds (MEDIUM)

`recover` (`packages/cli/src/lib.ts:155-157`) derives keys only for indices listed in the index
book. Lose the book (new device, restore from backup seed) and the refunds stay invisible. The
crate's refund memo (`wallet-core/src/lib.rs:88`, "a wallet puts in its own internal note … so a
restored wallet knows which refund index to watch") is never written on chain by this project, so
it doesn't help either. There is no gap-limit lookahead.

### 5. The MCP log is a world-readable ledger that links every swap (MEDIUM)

`ZSWAP_MCP_LOG` (`packages/mcp/src/tools.ts:10-12`) appends every call's full arguments and result
(recipient, every `refundTo`, signature, correlation id) to one file, created with the default mode
(0644 under the usual umask). The index book is written 0600 (`lib.ts:71`); the log, which links
just as much, is not.

### 6. Other links the product does not and cannot cut (documented or to document)

- **Amounts and timing.** The exact amount and a deadline go into every public request; three quotes
  one after another are a timing cluster. (Already listed as a limit in the docs.)
- **`ONECLICK_JWT`.** If set, the same partner token goes with every quote (`lib.ts:121`), so the
  provider can link the swaps privately even when the public data can't. Not mentioned anywhere.
- **Network origin.** All quotes come from one IP; not mentioned.
- **Refund to an Orchard-only UA is untested against 1Click.** The dry quote accepted the address,
  but no real refund ever went to one. Not mentioned.
- **Unbounded recovery range.** The MCP `recover` takes any `from_height >= 1` (`tools.ts:55`), so an
  agent can start a multi-million-block scan. Low severity.

### 7. What is right

- The index is reserved and written before the address is shown, and a failed quote burns its
  index rather than reusing it.
- Recovery streams compact blocks and trial-decrypts locally (`scan/src/lib.rs:311`). It never asks
  lightwalletd about a txid, so the server learns nothing about which outputs are the wallet's.
- `zswap swap` and `dry:false` are refused with BLOCKED (exit 3); there is no fake success.
- The treasury wallet is refused by path (`examples/src/zingo.ts:23`), and `recovery_info` is
  refused.

## Top fixes, ranked by impact / effort

1. **Dev server file access** (finding 1): allow only the dashboard, `deployments/` and
   `node_modules`, and deny `.demo/**`, `seed` and `*.dat`. Test: a real Vite dev server returns 403
   for a file under `.demo/` and for repo source, and 200 for the published run. Effort: S.
2. **Lock the index book** (finding 2): an exclusive `O_EXCL` lock file around every
   read-modify-write, a per-process temp name, and stale-lock recovery. Test: six real processes
   reserving at the same instant get six indices and six `refundTo`. Effort: S.
3. **Recipient-reuse guard** (finding 3): refuse a quote whose recipient already received an earlier
   swap from this book, unless the caller explicitly accepts the link (`--allow-linked-recipient` /
   `allow_linked_recipient`). Check before reserving, so no index is burned. Test: CLI library and
   MCP. Effort: S.
4. **Seed-only recovery** (finding 4): scan every booked index plus a lookahead window (`gap`,
   default 10) past the book's `next`, so an empty book still covers indices 0..9. Test: fresh seed,
   no book, and the scan uses `refund-0..9`. Evidence: the published refunds found from the demo seed
   with an empty book. Effort: S.
5. **Private MCP log** (finding 5): mode 0600, enforced even when the file already exists, and only
   `{at, tool, isError, index}` written, with no addresses, recipients or correlation ids. Test: the
   log's mode and contents after a live `safe_quote`. Effort: S.
6. **Honest copy** everywhere above, plus the limits: JWT, IP, Orchard-only refund untested, local
   ledgers. Effort: S.
7. Cap the recovery range per call (finding 6). Effort: S. Lower priority.
8. A real 1Click swap and refund on mainnet: **BLOCKED** (mainnet ZEC and Nick's OK; the crate also
   says no live addresses before review).

## One bold idea

**Cut all three links, not one.** The refund address is the easiest link to cut. The recipient and
the amount are the hard ones. Lethe could derive a fresh NEAR implicit account per swap from the
same seed (a one-time ed25519 key, the NEAR counterpart of the one-time IVK) and later sweep those
accounts through NEAR Intents. It could also split each swap into fixed denominations (0.05 / 0.1 /
0.2 ZEC) released at randomized delays, so every request looks like many others. Each swap would
then have its own refund address, recipient and amount bucket, and the link-budget panel could show
"0 shared fields" because it measured it. That would be a product, not a single fix.

### Still open after pass 2

- **Real swap: BLOCKED** (mainnet ZEC, Nick's OK, the draft derivation's review). So nothing has
  been delivered to a per-swap NEAR account, no sweep has been run, and no 1Click refund to a
  one-time Orchard address has been seen.
- **Lethe plans, it does not schedule.** The split and the delays are computed and the dry quotes in
  pass 2 were sent at the planned times by the run script, but there is no long-running scheduler
  for real swaps (they are BLOCKED).
- **Weak hints stay.** One destination token for the whole batch is shared by every part; the
  demo window put parts within ten minutes of each other. Both are in the report, not hidden.
- **Provider-side and network links.** A shared `ONECLICK_JWT` (the report marks it) and the IP.
- **Assets on other chains.** A fresh recipient is NEAR-only; for an asset delivered elsewhere the
  caller must bring a new address on that chain (the reuse guard still applies).
- **Sweeping** is advice plus a key export, not an executed flow; sweeping into one account
  re-links by construction.
- Spending a one-time Zcash note is still not integrated.
